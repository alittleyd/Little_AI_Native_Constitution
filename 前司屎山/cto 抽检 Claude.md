# CTO 初次勘查报告

**日期**: 2026-01-30
**范围**: 2025年及之后活跃项目
**扫描深度**: 全量代码结构 + 架构分析

---

## 1. 直观感受

**一句话**: "多头并进的野蛮生长"

四套主要业务系统（lb_shop、tp5.1-lubang、lubang-crm、zt-app）各自为战，框架版本从 Laravel 8 到 11 横跨四代，ThinkPHP 5.1 还在扛着最大的代码量（88K行）。能跑，但维护成本正在指数级上升。

---

## 2. 架构健康度

### 有架构吗？

**有，但执行不一致。**

| 项目 | 架构评分 | 诊断 |
|------|---------|------|
| **lb_shop** | ★★★★☆ | 最健康。Service层清晰（145个服务），事件驱动（30+31），Trait复用好 |
| **tp5.1-lubang** | ★★★☆☆ | 模块化但老化。ThinkPHP 5.1 框架本身已过时 |
| **lubang-crm** | ★★☆☆☆ | **问题最大**。服务层混在Http目录，Model层逻辑过重 |
| **zt-app** | ★★★☆☆ | 规模小，结构尚可 |

### God Class 警报

```
🔴 lubang-crm/app/Models/Lab.php                    → 2,070 行
🔴 lubang-crm/app/Http/services/IndexService.php    → 2,710 行
🔴 tp5.1-lubang/application/common/service/KdService.php → 3,234 行
🟠 lb_shop/app/Services/MultilingualEsSearchService.php  → 2,199 行
🟠 lb_shop/app/Services/Api/V1/OrderService.php     → 1,703 行
🟠 zt-app/app/Services/Kingdee.php                  → 2,579 行
```

**Lab.php** 是典型的 God Class：塞满了类型常量、合作阶段、研究方向、等级定义、业务计算逻辑。这不是Model，这是个垃圾场。

**IndexService.php** 更离谱：2,710 行的"统计服务"，处理 30+ 个关联模型。改一行，全身抖。

### Spaghetti Code？

没有明显的意大利面，但有"胶水代码"问题：

- ERP集成（金蝶）的逻辑集中在单个巨型文件（3234行）
- 多语言实现依赖大量 JOIN 查询，没看到缓存策略
- 审批流的 Clone 表设计增加了数据同步复杂度
- `common.php` 全局 helper 在多项目中存在，隐式耦合

---

## 3. 潜在风险

### 如果现在要加一个新功能，最大的风险是什么？

**答案：不知道改哪里，也不知道会影响哪里。**

| 风险 | 严重程度 | 说明 |
|------|---------|------|
| **框架版本地狱** | 🔴 高 | Laravel 8/9/10/11 + ThinkPHP 5.1 共存，依赖冲突概率极高 |
| **God Class 连锁反应** | 🔴 高 | 改 Lab.php 或 IndexService.php，回归测试是噩梦 |
| **ERP 集成是单点故障** | 🔴 高 | KdService 3234 行，金蝶接口变动会导致大面积修改 |
| **测试覆盖薄弱** | 🟠 中 | lb_shop ~31个测试文件；lubang-crm/zt-app 各~4个；tp5.1-lubang 基本无测试 |
| **无可见的 CI/CD** | 🟠 中 | 没看到自动化测试和部署流程 |
| **配置泄露风险** | 🟠 中 | 多个项目 .env 内存在真实 DB/Redis/Mail 凭据 |

**最坏情况**: 新功能涉及 CRM 和 ERP 联动，需要同时改 lubang-crm 的 God Class 和 tp5.1-lubang 的 KdService，没有自动化测试兜底，上线就是开盲盒。

## 4. 数据库设计

### 反常识的地方

**1. 多语言表设计 — 合理但有性能隐患**

```
products → products_lang (1:N, lang字段区分语言)
```

设计本身没问题，但每次查询都要 JOIN 语言表。没看到索引优化策略，大数据量下会成为瓶颈。`lang` 多语言表缺少唯一约束，易产生重复语言数据。

**2. 审批流的 Clone 表设计 — 有创意但复杂**

```
原表 → *_clone（编辑中）→ *_approval（审批中）→ 回写原表
```

理解为什么这么做（编辑不影响线上数据），但数据同步逻辑分散在多处，容易出现不一致。

**3. 时间戳不一致**

广泛使用 `create_time/update_time/delete_time` 整型时间戳，和 Laravel 默认 timestamps/softDeletes 不一致，增加维护成本。

**4. 反范式字段**

如 `recommend_article_ids`/`recommend_list_ids` 以字符串保存多 ID，后续查询/索引/一致性成本高。

## 一、Level 定级

### 业务责任等级判定

根据宪法第 310-316 条"从 Level 2 升级到 Level 3 的信号"：

> - [ ] 涉及金钱/核心数据（零容错）

**事实认定**:
- ✅ 存在支付系统集成（yansongda/pay - 支付宝/微信支付）
- ✅ 存在订单管理系统（OrderService 1703行+）
- ✅ 存在 ERP 财务集成（金蝶 KdService 3234行）
- ✅ 存在 CRM 客户/合同/应收款管理

**判定**: 业务责任等级 = **Level 3（可交付工程）**

---

### 实际工程纪律等级判定

根据宪法特征矩阵对比：

| 维度 | Level 3 要求 | 实际情况 | 符合 |
|------|-------------|---------|------|
| 文档 | 完整文档（PRD + TDD + API Doc） | lb_shop 有 CLAUDE.md，其余缺失 | ❌ |

| 风险 | 低（完全可控） | 高（上线开盲盒） | ❌ |

**判定**: 实际工程纪律 = **Level 2 下限，局部 Level 1**

## 二、违宪证据（反模式 3：偷偷变化）

根据宪法第 361-381 条"反模式 3：偷偷变化 (Hidden Escalation)"：

> ```
> 最不专业的情况：
> 用Level 1的纪律，承担Level 3的后果
> ```

### 证据清单

| 证据编号 | 违宪事实 | 代码位置 | 严重程度 |
|---------|---------|---------|---------|
| **E-001** | God Model：业务逻辑塞进 Model | `lubang-crm/app/Models/Lab.php` (2070行) | 🔴 严重 |
| **E-002** | God Service：统计逻辑集中单文件 | `lubang-crm/app/Http/services/IndexService.php` (2710行) | 🔴 严重 |
| **E-003** | God Service：ERP 全部逻辑单点 | `tp5.1-lubang/.../KdService.php` (3234行) | 🔴 严重 |
| **E-004** | 测试覆盖接近于零 | `tp5.1-lubang/tests/` 不存在 | 🔴 严重 |
| **E-005** | 隐式耦合：全局 helper | `*/common.php` 多处存在 | 🟠 中等 |
| **E-006** | 配置泄露：.env 含真实凭据 | 多项目 `.env` 文件 | 🟠 中等 |
| **E-007** | 框架版本割裂 | Laravel 8/9/10/11 + ThinkPHP 5.1 | 🟠 中等 |

### 违宪认定

宪法原文：
> ├─ 用户遇到bug → 修不了（代码太乱）
> ├─ 用户要新功能 → 不敢加（改一处崩全局）
> └─ 技术债爆炸

**现状完全吻合**：
- Lab.php 2070 行 → 改一行影响 CRM 全局
- KdService 3234 行 → 金蝶接口变动需大面积修改
- 无自动化测试 → 每次上线都是开盲盒

**判定**: ✅ **违反反模式 3：偷偷变化**

## 三、OSI 思维审查

根据宪法第 55-92 条"OSI 七层故障排查 → 软件问题诊断"：

> **问题应该在"最合适的层"解决**

### 分层架构检查

**理想分层**:
```
表示层（API/Controller）
    ↓
应用层（Service - 业务编排）
    ↓
领域层（Domain - 核心业务逻辑）
    ↓
数据访问层（Repository/Model - 数据操作）
    ↓
基础设施层（DB/Cache/外部系统）
```

**实际情况**:
```
Controller
    ↓
Service（业务逻辑 + ERP调用 + 数据访问 混在一起）
    ↓
Model（数据操作 + 业务常量 + 计算逻辑 混在一起）
    ↓
DB + 金蝶 + Elasticsearch（直接耦合）
```

### 层间混杂证据

| 问题 | 位置 | 违反原则 |
|------|------|---------|
| Model 层混入业务逻辑 | `Lab.php` 含类型常量、等级计算 | 应在 Service/Domain 层 |
| Service 层混在 Http 目录 | `lubang-crm/app/Http/services/` | 关注点混淆 |
| ERP/DB/业务 在同一 Service | `KdService.php` 3234行 | 应分离为 Client + Service |
| 全局函数隐式耦合 | `common.php` 散落各处 | 应封装为 Utility 类 |

**判定**: ❌ **未形成清晰的 OSI 分层映射，呈现"层间混杂"**

---

## 四、最终判决

### 判决选项

- [ ] 建议重构 (Refactor)
- [x] **建议分阶段重写 (Strangler Pattern Rewrite)**
- [ ] 建议销毁 (Destroy)

### 裁定理由

1. **不选"重构"**: God Class 规模过大（2000-3000行），重构成本已接近重写
2. **不选"销毁"**: 系统承载核心业务，正在运行，有商业价值
3. **选择"分阶段重写"**: 采用 Strangler 模式，边运行边替换

### 执行建议

```
Phase 1: 冻结（1-2周）
├─ 冻结 lubang-crm 和 tp5.1-lubang 新功能开发
├─ 建立 CI/CD 流程
└─ 为 God Class 补充关键路径测试

Phase 2: 绞杀（持续）
├─ 以 lb_shop 为架构标杆
├─ 新功能写在新服务中，通过 API 调用旧系统
├─ 逐步将旧逻辑迁移到新架构
└─ 旧模块逐个下线

Phase 3: 统一（最终）
├─ 统一到 Laravel 11 + 统一目录结构
├─ 淘汰 ThinkPHP 5.1
└─ 实现完整测试覆盖
```
